# 自動レビュー（合格するまで、各段階で最大5回）

ES は、書き手が伝わっているはずだと思い込んでいる部分ほど見えにくい。
そこで、ユーザーに見せる**前に**2つの段階で審査し、合格するまで直す。
時間とクレジットを抑えるため、機械的に判定できるものはスクリプトで先に落とし、別のレビュアー（サブエージェント）は判断が必要な段階 O だけに使う。

| 段階 | タイミング | 誰が審査するか | 対象 | 記録先 |
|---|---|---|---|---|
| P. プランレビュー | 骨子（`plan.md`）を作った直後、本文を書く前 | 自分（チェックリストで機械的に判定） | `plan.md`、設問原文、企業リサーチメモ | `reviews/plan_r{N}.md` |
| O. 出力レビュー | `es_lint.py` が OK になった後、追記・報告の前 | 別のレビュアー（Sonnet のサブエージェント） | `bundle_output_r{N}.md` だけ | `reviews/output_r{N}.md` |

作業ディレクトリ（以下 `$W`）は、スクラッチパッドがあればその中の `es_work/企業名_設問略称/`、無ければ `/tmp/es_work/企業名_設問略称/`。リポジトリ内には置かない。

## ループの規則

1. レビューを実行し、判定（PASS / FAIL）と指摘を記録先に保存する。
2. **PASS** → 次の工程へ進む。
3. **FAIL** → 要修正をすべて直す（段階 O では直した後に `es_lint.py` を再実行し OK にしてから）→ 回数を1つ進めて、もう一度レビューする。
4. レビューは**各段階で最大5回**。5回目も FAIL なら、それ以上は直さずに止め、残った指摘をユーザーに示して判断を仰ぐ（段階 P なら骨子と一緒に、段階 O なら報告の「確認事項」として）。
5. 「提案」は直さなくても合格扱いにしてよい。直さなかった提案は報告に一行で残す。
6. 指摘に応えるために事実を足さない。正典表・過去回答・ユーザー発言・リサーチメモに無い情報が必要なら、本文に入れず「確認事項」に回す（その指摘は「要確認」として PASS を妨げない）。
7. 段階 O で「骨子から崩れている」（エピソードの選択や結論が不適切）と判定されたら、段階 P に戻り、P のレビューを1回目からやり直す。O の回数はそのまま引き継ぐ（無限ループを防ぐため、O は通算5回まで）。
8. 同じ指摘が2回続けて直らない場合は、直し方を変える（言い換えではなく、段落構成やエピソードの選択から見直す）。

## レビューの実行方法

### 段階 P（自分で判定する）
骨子は短く、判定もチェックリストで足りるので、サブエージェントは使わない。作成時の意図はいったん脇に置き、`plan.md` を読み直して P1〜P7 と lessons.md の教訓を1項目ずつ ○ / ✕ で判定し、記録ファイルに書く。

### 段階 O（別のレビュアーに任せる）
1. 機械チェックを先に通す。`es_lint.py` が NG の間はレビュアーを呼ばない（呼んでも同じ指摘が返るだけで、トークンを使う）。
   ```bash
   python3 .claude/skills/es-coach/scripts/es_lint.py --file $W/draft.txt --limit 500 --mode within
   ```
2. レビュー資料を1ファイルにまとめる。本文・骨子・lint 結果・採点基準・正典表・教訓・その企業の修正履歴と使用済みエピソード・リサーチメモ・前回の指摘が入る。
   ```bash
   python3 .claude/skills/es-coach/scripts/review_bundle.py --workdir $W --company MIXI --question "設問原文" --limit 500 --mode within --round N
   ```
3. Agent ツールで、毎回**新しい**レビュアーを `model: "sonnet"` で起動する。前回のやり取りは引き継がない（作成者の意図を知らない初見の採用担当として読ませるため）。依頼文は下のテンプレート。レビュアーには資料ファイル以外を読ませない。
4. **2回目以降は差分だけ審査させる。** 前回の要修正が直ったかと、直したことで新しく生じた問題だけを見る。点数は前回から変わった項目だけ付け直す。
5. サブエージェントが使えない場合は、資料ファイルを自分で読み、同じ手順で判定する。

## ナレッジの参照と記録

- `history/lessons.md` の教訓はチェックリストに追加する項目として扱い、**違反は要修正**。段階 P では作業開始時に読んだ `knowledge.py brief` の内容を使い、段階 O ではレビュー資料に入っている。直近の修正履歴と同じ種類の誤りが繰り返されていたら、指摘に「過去にも同じ指摘あり」と書く。
- 「要修正」を1件直すたびに、`references/knowledge.md` に従って記録する（`knowledge.py add --stage plan|output --source review --round N`）。

## 判定基準

- **要修正**（1件でもあれば FAIL）
  - 段階 P: チェックリスト P1〜P7 のいずれかを満たさない。
  - 段階 O: `rubric.md` の自動不合格に該当／8項目の合計が 13 点未満／0点の項目がある／「選考通過の観点」S1〜S6 のいずれかが ✕。
- **提案**（PASS を妨げない）: 通過率をさらに上げる言い回し、段落順、エピソードの見せ方など。
- **要確認**（PASS を妨げない）: ユーザーに聞かないと直せない事実・数値。

## チェックリスト

### 段階 P: プラン（骨子）

- [ ] **P1 設問の分解**: 設問原文に含まれる問いをすべて列挙し、それぞれに対応する段落がある（「目的、目標」のように2つ聞かれていたら2つとも）。
- [ ] **P2 結論1文**: 冒頭に置く結論1文が書かれていて、それだけで設問に答えている。
- [ ] **P3 評価してほしい一点**: 「この回答で採用担当に残したい評価ポイント」が1つに絞られて明記されている（例:「チームの開発速度を仕組みで上げられる人」）。全段落がその一点を支えている。
- [ ] **P4 求める人物像との対応**: 企業の求める人物像・バリュー・職種要件（リサーチメモ、無ければ設問文から読み取れる意図）のどれに対応させるかが書かれている。自己PR・ガクチカでも、リサーチ済みの企業なら対応先を1つ選ぶ。
- [ ] **P5 素材の適切さ**: エピソードは1本（自己PR・ガクチカ）。数値は正典表のものだけ。同じ企業の他設問で使ったエピソードと重複していない（`es_index.py --episodes --company`）。時制が今日基準で正しい。
- [ ] **P6 差別化**: 「この人にしか書けない要素」（自分の判断・工夫・固有の経験）がどこに入るか書かれている。誰でも書ける一般論の段落になっていない。
- [ ] **P7 字数配分**: 段落ごとの目安字数の合計が上限の 90〜100%（以内）に収まり、配分が `question-types.md` の目安から大きく外れていない（行動・成果の段落が最も厚い）。

### 段階 O: 出力（本文）

1. `rubric.md` の自動不合格4条件と8項目を採点する（各項目に原文引用を根拠として付ける）。文字数・一文の長さ・口癖・誇張・NG表現は lint 結果をそのまま使い、読み直さない。lint の WARN（正典表に無い数値、「」の使い方、記号）は判断して要修正か否かを決める。
2. `rubric.md` の「選考通過の観点」S1〜S6 を ○ / ✕ で判定する。
3. `plan.md` との一致: 骨子の結論と評価ポイントが本文に残っているか。崩れていたら規則7。
4. 前回指摘の対応状況（2回目以降）。

## レビュアーへの依頼文（テンプレート）

```
あなたは新卒採用の書類選考を担当する、厳しめの採用担当兼ESレビュアーです。作成者とは別人として、初見で読んでください。
次の資料ファイル1つだけを読み、他のファイルやスクリプトは読まないでください（必要な情報はすべて入っています）。編集もしないでください。

- 資料: {$W/bundle_output_r{N}.md}

審査の手順:
1. 自動不合格4条件と8項目を採点する。文字数・一文の長さ・口癖・誇張・NG表現は資料内の機械チェック結果をそのまま使う。
2. 選考通過の観点 S1〜S6 を ○ / ✕ で判定する。
3. 骨子の結論と評価ポイントが本文に残っているかを見る。崩れていたら「骨子から崩れている」と書く。
4. 蓄積した教訓への違反は要修正にする。AIらしい書き方（普通の語を「」で強調、決め台詞、抽象語の飾り）も要修正。
5. {2回目以降のみ: 前回の指摘が直ったかと、直したことで生じた新しい問題だけを見る。点数は変わった項目だけ付け直す。}

判定: 自動不合格なし・13点以上・0点の項目なし・S1〜S6 すべて ○ なら PASS、それ以外は FAIL。
最後に「この ES で書類選考を通すか、落とすか」を一言で判断し、落とす場合はその理由を要修正に入れてください。
推測で合格させないでください。確認できなかった項目は未確認と書いてください。
出力は次の形式で、600字程度までに収めてください（良い点の説明は不要）。

{下の「出力形式」をそのまま貼る}
```

## 出力形式（記録ファイルの中身）

```markdown
# 段階{P|O} レビュー 第{N}回
判定: PASS | FAIL
書類選考の判断: 通す | 落とす（理由1行）

## スコア（段階 O のみ）
- 自動不合格: なし | あり（条件名）
- 8項目: 14/16（0点: なし / 1点: #3 数値, #5 企業接点）
- 選考通過の観点: S1 ○ / S2 ○ / S3 ✕ / S4 ○ / S5 ○ / S6 ○

## 要修正
1. [S3 差別化] 第2段落「チームで協力して課題を解決しました」は誰でも書ける。PR分割を選んだ判断理由を書く。
## 提案
1. …
## 要確認
1. …
## 未確認
1. …
## ナレッジとの関係
- 過去にも同じ指摘あり: …（該当すれば）
## 前回指摘の対応状況（2回目以降）
- 第{N-1}回 要修正1: 対応済 / 未対応
```
