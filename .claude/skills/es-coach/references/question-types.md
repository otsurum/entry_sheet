# 設問タイプ別の型

設問文を読んで下のどれかに分類し、その節だけ読む。複合設問（「経験と、それをどう活かすか」）は2つの型を連結する。
各節: 構成テンプレ（段落と字数配分）→ この人の素材で刺さるもの → 過去回答の落とし穴。

字数配分は「400字なら」の目安。他の上限は比例させる。

## 1. 志望動機

企業リサーチ必須（`company-research.md`）。

構成（400字）:
1. 結論 60字: 「志望理由は、〜（企業固有の事実）で〜したいからです」
2. 原体験・価値観 120字: なぜそう思うようになったか。エピソード1つ、数値1つ。
3. 企業との接点 140字: 企業の固有名詞2つを自分の経験・価値観と1対1で結ぶ。
4. 入社後の貢献 80字: 持ち込める強みと、伸ばしたいこと。

刺さる素材:
- チーム協働を掲げる企業 → PR分割・デモ動画で約1か月短縮、リモートの情報共有、対話ロボット研究（サイボウズ回答が型）
- toC・UX 重視 → mecap への家族フィードバック → iPad→iPhone 再設計（pixiv 回答が型）
- コミュニケーション・コミュニティ系 → 対話ロボット研究＋MIXI「興味を持ったきっかけ」回答

落とし穴:
- 「貴社」連発、「多様な事業」「成長できる環境」（リクルート回答）
- 他のどこにも出てこないエピソード（リクルート回答の「ドキュメント自動生成スクリプト」）。面接で深掘りされて説明できない。
- 「インターンを志望」「インターンでは〜したい」の残存。
- 会社説明の書き写しで自分の話が無い。

## 2. 自己PR・強み

構成（400字）:
1. 結論 40字: 「私の強みは〜です」（`self_introduce.md` の「代表的な自己PRの核」5パターンから選ぶ。1つだけ）
2. 課題 60字 → 行動 140字 → 成果 60字（数値）
3. 学び・再現性 60字: その強みが別の場面でも発揮された事実、または入社後の活かし方
4. （余れば）入社後の活かし方 40字

刺さる素材:
- 強み10項目から、企業タイプに合う1つ（`self_introduce.md`「自己PRの方向性メモ」で選ぶ）
- 未使用の強い数値「タスク約1か月短縮」（PR分割・デモ動画・事前レビュー）
- 「既存の設計思想を読み解いてから実装する」は iOS 職向けに強い

落とし穴:
- 強みを2つ以上並べて薄まる（Sansan 回答は iPhone 対応と React 適応と勉強会を全部入れて 1052 字）
- 「成長できた」で終わる主観成果
- ドワンゴ「強み」回答は 400 字目安に対し 782 字。エピソード3本は多い、1本に絞る。

## 3. ガクチカ・成果エピソード・一番成長した経験

構成（400字）:
1. 結論 40字: 「一番成長した経験は〜です」
2. 状況・課題 80字: プロダクト、チーム規模、自分の役割、何が問題だったか
3. 自分の判断と行動 160字: なぜその方法を選んだか、誰とどう認識を合わせたか
4. 成果 60字: 数値、または第三者が確認できる事実
5. 学び・再現性 60字

刺さる素材（`self_introduce.md`「面接で話せる具体エピソード」の7本）:
- **AR 倉庫シミュレーションアプリの不具合修正（3日）**: 本選考の主軸。再現条件の固定 → ログで処理順を可視化 → 仮説（アンカー復元とデータ読込の順序）→ 検証 → 修正 → 実機確認。「困難を乗り越えた経験」「粘り強さ」「仮説検証」系に最優先で使う。ES に書く前に「要確認」項目（フレームワーク名、外れた仮説、次に活きた例）を確認事項として出す。
- **要件の解像度が低いまま着手して手戻り**: 失敗談。着手前の疑問洗い出しとマネージャーとの認識合わせを習慣化 → kubell でユーザーストーリーから要件を考える側へ。「失敗から学んだこと」「チームで働く上で大切にしていること」に使う。自責と環境の切り分けを必ず書く。
- iPad→iPhone 対応（最頻出7社。使うなら「設計思想を読んでから」「Figma で事前に認識合わせ」の判断理由を厚く）
- React/FastAPI 適応 → API リクエスト削減（AI をメンターにした学習戦略。削減率の数値は書かない）
- PR分割・デモ動画 → 約1か月短縮（企業別回答で未使用）
- 不具合修正（発生条件の整理 → マネージャーへ共有 → 関数を1つずつ追う → 影響範囲を見て修正）
- 夏インターン3社（チームラボ: 保守運用とバックログ管理、サイボウズ: インターン生主体で要件洗い出し〜AI要約実装、kubell: ユーザーストーリー作成から実装）。まだ ES に書いていないので新鮮。詳細は entry_sheet.md L44〜L63。

落とし穴:
- 「頑張った」「成長できた」の主観成果（freee 回答は良い例: 成果を「iPhone でも自然に利用できる形に落とし込み、利用可能な環境を広げた」と事実で書いている）
- チームの成果と自分の行動の混同

## 4. 研究内容

素材が薄い（GREE 回答の1段落のみ）。**初回は必ずヒアリング**: 研究の目的（誰の何を解決）、自分の担当範囲、手法、評価指標、現時点の結果、今後の予定、学会発表の有無。回答後、`self_introduce.md` に研究節を追記するようユーザーに提案する（Skill が勝手に追記はしない）。

構成（500字）:
1. 目的 80字: 対話ロボットで「誰の・何を」良くしたいか
2. アプローチ 150字: NLP による応答生成、親しみやすさを与える応答戦略、間・相槌・リアクションのタイミング
3. 評価方法 100字: 性格特性・感情の観点からの定量評価、対話ログ分析
4. 現状と自分の担当 100字
5. 仕事との接続 70字: コミュニケーションの質への関心 → チーム開発・プロダクトの UX

落とし穴: GREE 回答は成果・担当範囲・学びが無く 357/500 字（71%）。

## 5. キャリアビジョン・将来像・活躍イメージ

構成（400字）:
1. 結論 60字: 3〜5年後の姿を1文で（「技術の深さと事業視点を両立したエンジニア」が既存の軸）
2. 根拠となる現在の行動 160字: 既にやっていること（設計思想を読む、勉強会登壇、NovelAssistEditor での再現）
3. 伸ばしたいこと 100字: 自認する弱み3つ（テスト / 大規模 / 要件定義）から企業に合うもの1つ
4. その会社でどう実現するか 80字: 企業固有の事実と結ぶ（企業リサーチ）

刺さる素材: DeNA「ソフトウェアエンジニアとしての課題」「取り組み」（他人から学ぶ / 知見を蓄積 / アウトプット の3軸）、Sansan「キャリアヴィジョン」の骨子（技術面と事業面）。

落とし穴: Sansan 回答は抽象語のみで数値・固有名詞なし。「なりたい」だけで「今やっている」が無いと信用されない。

## 6. 入社後に挑戦したいこと・やりたいこと

企業リサーチ必須。

構成（500字）:
1. 結論 60字: 「〜に挑戦したいです」
2. 現状の限界 120字: 3〜4名チームでの経験の範囲、テスト・スケーラビリティ経験の不足（事実として）
3. この会社でこそできること 160字: 企業固有名詞（プロダクト、規模、技術的取り組み）と結ぶ
4. 具体テーマ 100字: Swift Testing × TCA、大規模データ、上流工程 など1つ
5. 持ち込める強み 60字: 数値1つ

刺さる素材: MIXI「挑戦してみたいこと」回答（L793）の骨子、弱み3つ、Swift Testing への取り組み。

落とし穴: 「インターンシップでは」の残存。企業固有性のない一般論。

## 7. 注目しているサービス・技術

構成（500字）:
1. 対象 40字
2. 注目理由 150字: 何が変わった／何が問題か
3. 課題と改善案、または自分の学習状況 200字: 実装の視点を1つ入れる（アルゴリズム、設計、テスト）
4. 自分の開発との接続 110字

刺さる素材: X のアルゴリズム分析（GREE）、Swift Testing × TCA（MIXI L783。519字→削る必要あり）、Swift Concurrency。

落とし穴: 感想だけ。自分が試したことが無い。

## 8. AI 活用・開発プロセスの工夫

構成: 事例3つ（各: 場面 → やり方 → 効果）→ メタ的な気づき1段落。
メルカリ回答（L294〜）がほぼ完成形。改善率の数値（30〜40%、60〜70% 等）は根拠がないため書かない。

落とし穴: 「AI に任せた」で主体性が消える。「AI の出力を自分で検証する」姿勢を必ず1文入れる。

## 9. プロダクト説明・ポートフォリオ

構成: 一文要約 → 解決した課題 → 主要機能3つ（箇条書き可）→ 技術と設計判断（なぜ TCA / SPM か）→ URL。
素材: mecap（GREE L177〜）、NovelAssistEditor（MIXI L695〜 が 400 字版、DeNA L343〜 が長文版）、工事現場アプリ（DeNA L449〜）。URL は entry_sheet.md からコピー。

落とし穴: DeNA 回答は 2146 字。上限が無くても 800 字程度で止める。

## 10. キャッチコピー・一言系

構成: **コピー本体**（上限内。名詞句か体言止め。「〜するエンジニア」「〜から書く人」）→ 理由はエピソード1つで（課題 → 行動 → 気づき）。

候補の方向:
- UX 原体験系: 「動くだけでは足りない、と家族に教わったエンジニア」（mecap）
- 設計理解系: 「読み解いてから書く」「既存の設計に敬意を払う実装者」
- チーム系: 「レビューされやすさから設計する」

落とし穴: **WealthNavi 回答はコピー本体が無い**。設問に答えているかを最初に確認する。理由にエピソードを2つ以上詰めない。

## 11. 逆質問

企業リサーチ必須。「調べれば分かること」は聞かない。
型（freee 回答）: 「成長している若手エンジニアに共通する行動は」「新卒が最初の半年〜1年で期待されるアウトプットは」。
企業固有版: 技術ブログで見た取り組みについて「〜の導入で、レビューや品質保証のプロセスはどう変わりましたか」のように、自分の関心（テスト、AI 活用、設計）と結ぶ。2〜3個。

## 12. 弱み・課題

構成（400字）: 弱み1つ 40字 → 自覚した場面 100字 → 取り組み 160字 → 変化・現状 100字。
素材: テストコード習慣（NovelAssistEditor に Swift Testing 導入中）、要件定義力（kubell インターンでユーザーストーリー作成を経験）、大規模データ（勉強会で「将来必要になる知識の基盤」を作る姿勢）。DeNA「課題」「取り組み」回答が詳細版。

落とし穴: 弱みに見えない弱み（「こだわりすぎる」）。取り組みが「勉強したい」だけで現在進行形の事実が無い。

## 14. 失敗から学んだこと・困難を乗り越えた経験

構成（400字）: 結論 40字（何を学んだか）→ 状況と失敗・困難の中身 100字（自分の判断がどう間違っていたか、または何が見えなかったか）→ 立て直しの行動 140字（手順として）→ 結果 60字 → 今どう行動が変わったか 60字。

刺さる素材:
- 失敗系 → 「要件の解像度が低いまま着手して手戻り」。焦りから確認を省いた自分の判断を自責として書き、環境要因（自主性重視で確認の仕組みが無かった）は言い訳にせず「だから自分で仕組みを作った」に転換する。
- 困難系 → 「AR 倉庫アプリの不具合修正（3日）」。2つの不具合が絡んで最初は別問題だと分からなかった、という「見えなかったこと」を課題にする。

落とし穴: 失敗の原因を環境に置く。「学んだ」だけで、その後の行動の変化と証拠（手戻りが無くなった、kubell で要件側に立てた）が無い。失敗の規模が小さすぎて失敗に見えない（1〜2日の遅れは「レビューで作り直し」という事実を添えれば十分伝わる）。

## 13. エンジニアを目指したきっかけ・原体験

構成（400字）: きっかけの場面 100字 → 最初の行動（独学で mecap を作った）100字 → 転機（家族の指摘）100字 → 今の姿勢 100字。
素材: DeNA「エンジニアを目指したきっかけ」（1120字の長文版）。

落とし穴: 「言葉に尽くしがたい」など感情表現の過剰。事実で書く。
